## 1. 一言でいうと

> **小さなお店の「予約帳」をスマホ／ネットに置き換え、無断キャンセルをリマインドで減らす月額サービス。**

お客さんは公開の予約ページから予約 → お店は管理画面で確認 → 前日に自動でリマインドが飛ぶ。
この一連を、お店が **月額数百〜数千円** で使う形です。

---

## 2. 解決したい課題

ターゲットとなる「1人で店を回している人」が日常で困っていること：

| 課題 | 今どうしているか | それの何が辛いか |
|---|---|---|
| 予約管理 | 紙の手帳・LINE・電話 | 二重予約、書き間違い、外出先で確認できない |
| 無断キャンセル | 何もしていない | 1枠の損失が大きい（1人店は1日数枠しかない） |
| リマインド | 手動でLINE送信 | 毎回手作業、送り忘れる |
| 顧客情報 | 記憶 or バラバラのメモ | 「前回いつ来た？何が好き？」が分からない |
| 営業時間外の予約受付 | できない（寝てる・施術中） | 機会損失。電話に出られず取り逃す |

**一番刺さるのは「無断キャンセルを減らせる」と「24時間ネットで予約を受けられる」の2点**です。
これは売上に直結するので、お金を払う理由になります。

## 3. ターゲット（誰に売るか）

### メイン
- 美容室・ネイル・まつエク・エステ
- 整体・鍼灸・マッサージ
- パーソナルトレーナー
- ピアノ／英会話などの個人教室

### 共通する特徴
- **1人〜数人**で運営（大手予約システムはオーバースペック＆高い）
- 1日の予約枠が限られる（だから1件のキャンセルが痛い）
- IT に詳しくない → **「簡単」が最重要**

### 最初の1人（ペルソナ）
> 35歳、自宅サロンでネイルを1人で運営。予約は Instagram のDMと LINE。
> 手帳に書き写していて二重予約をやらかしたことがある。
> 無断キャンセルが月2〜3件あり、地味に売上が削れている。

## 4. 提供する機能

### MVP（最初に必ず作る最小機能）
SaaS の3大要素（アカウント・クラウド保存・課金）＋核となる予約機能。

1. **アカウント登録／ログイン**（お店側）
2. **公開予約ページ**（`reserva.app/お店の名前` のようなURL）
   - 営業時間・メニューを設定 → お客さんが空き枠を選んで予約
3. **予約管理ダッシュボード**（お店側）
   - 今日／今週の予約一覧、手動での追加・変更・キャンセル
4. **自動リマインド**（メール。前日 or 当日朝に自動送信）
5. **顧客リスト**（誰がいつ来たかの履歴）

### Phase 2（有料プランの価値を上げる）
- LINE 連携リマインド（日本では効果大）
- 複数スタッフ・複数メニューの枠管理
- 事前決済・キャンセルポリシー（カード登録で無断キャンセル抑止）
- Google カレンダー同期
- 簡単な売上レポート

### あえて作らないもの（スコープ外）
- POS・レジ機能、在庫管理、給与計算 → 別ジャンル。手を広げない。

## 5. 収益モデル（どう稼ぐか）

**フリーミアム + 月額サブスク**（SaaS の王道）。

| プラン | 月額 | 内容 | 狙い |
|---|---|---|---|
| Free | 0円 | 予約 月30件まで／リマインドはメールのみ | まず使ってもらう入口 |
| Pro | 1,480円 | 予約無制限／LINEリマインド／顧客カルテ | メインの収益源 |
| Business | 3,980円 | 複数スタッフ／事前決済／レポート | 伸びた店向け |

### 数字のイメージ
- Pro 100店契約 → **月14.8万円**の継続収入
- Pro 500店契約 → **月74万円**
- ポイントは「契約が積み上がる」こと。買い切りと違い、来月も再来月も入る。

### 課金の仕組み
- **Stripe**（ストライプ）という決済サービスを使う。
- クレジットカード情報は Stripe が預かるので、こちらでカード番号を持たない（安全・実装が楽）。

## 6. 技術構成（どう作るか）

「1人で・低コスト・低運用」を最優先にした構成。

| 役割 | 採用技術 | 理由 |
|---|---|---|
| 画面・サーバー | **Next.js**（React系） | 既存の React スキルが活きる。1つで画面もAPIも書ける |
| 言語 | **TypeScript** | 型があるとバグが減る（既存プロジェクトと同じ） |
| 見た目 | **Tailwind CSS** | 既存プロジェクトと同じ。素早くUIを作れる |
| DB・認証 | **Supabase** | Postgres DB + ログイン機能 + データ分離が一体。無料枠あり |
| 課金 | **Stripe** | サブスク課金の定番。日本対応 |
| メール送信 | **Resend** | リマインドメール送信。実装が簡単 |
| ホスティング | **Vercel** | Next.js を git push するだけで公開。無料枠あり |

### マルチテナントの考え方（重要）
SaaS は「複数のお店が1つのシステムを共有する」形（=マルチテナント）。
**A店のデータが B店から見えてはいけない**。
これを Supabase の **RLS（Row Level Security）** という仕組みで、DB レベルで強制的に分離する。
→ アプリのバグでうっかり他店のデータを出す事故を防げる。

### データ構造（ざっくり）
```
shops        … お店（テナント）。1アカウント=1ショップ
  └ services … メニュー（カット, ネイル等／所要時間・料金）
  └ bookings … 予約（日時・お客・メニュー・ステータス）
  └ customers… 顧客（名前・連絡先・来店履歴）
  └ subscription … 契約プラン（Stripe と連携）
```

## 8. ざっくりコスト

開発中・小規模なうちは **ほぼ無料** で回せる構成。

| 項目 | 初期 | 備考 |
|---|---|---|
| Supabase | 無料 | 小規模なら無料枠で足りる |
| Vercel | 無料 | 個人利用は無料枠 |
| Stripe | 無料 | 決済が発生した分だけ手数料（約3.6%） |
| Resend | 無料〜 | 月3,000通まで無料 |
| ドメイン | 年1,000〜2,000円 | `reserva.app` など |

→ **お金がかかり始めるのは「ユーザーが増えてから」**。これは良い兆候（=売上も出ている）。

## 9. リスクと対策

| リスク | 中身 | 対策 |
|---|---|---|
| 競合が多い | STORES予約, リザービア 等の既存サービス | 「1人店・激安・超シンプル」に絞って差別化。全部入りで戦わない |
| 作っても使われない | 一番ありがちな失敗 | 作り込む前に1店舗に試用してもらい、反応を見る（段階6を前倒し） |
| IT 苦手な層が離脱 | 設定が難しいと使われない | オンボーディングを徹底的に簡単に。初期設定を最小に |
| 個人情報の扱い | 顧客の連絡先を預かる | RLSでの分離、最小限の取得、プライバシーポリシー整備 |
| 1人で続けられるか | 開発・運用・サポートが全部自分 | 機能を欲張らない。自動化できるところは自動化 |

## 10. 用語集（はじめての人向け）

| 用語 | 意味 |
|---|---|
| **SaaS** | ネット越しに使ってもらい、月額でお金をもらい続けるソフトのビジネス形態。例: Netflix, Notion |
| **サブスク** | 月額・年額などの継続課金。SaaS の主な収益モデル |
| **フリーミアム** | 基本無料＋高機能は有料、という料金設計。まず使ってもらう入口を作る |
| **MVP** | Minimum Viable Product。「最低限これがあれば価値が出る」最小構成。最初はこれだけ作る |
| **マルチテナント** | 1つのシステムを複数の顧客（お店）で共有する作り。各社のデータは厳密に分離する |
| **テナント** | マルチテナントにおける1顧客の単位。Reserva では「1つのお店」 |
| **RLS** | Row Level Security。DBの行ごとにアクセス権を制御し、他テナントのデータを見せない仕組み |
| **オンボーディング** | 新規ユーザーが使い始める導入体験。ここが難しいと離脱する |
| **Stripe** | 決済代行サービス。カード課金・サブスク管理をやってくれる定番 |
| **Webhook** | 「課金が成功した」等のイベントを Stripe からこちらのサーバーへ自動通知する仕組み |
| **Supabase** | DB（Postgres）＋ログイン認証＋データ保存を一体で提供するサービス |
| **Next.js** | React を使った Web アプリ／サイトを作るための定番フレームワーク |
| **Vercel** | 作った Next.js アプリをネットに公開するためのホスティングサービス |
